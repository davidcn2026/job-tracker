## 一、已定结论（不用再讨论）

### 1. 招聘渠道分组与唯一约束

**结论**：唯一约束从 `(user_id, company, position)` 改为 `(user_id, company, position, source)`。

| 场景 | 结果 |
|---|---|
| 同公司同岗位 + 同渠道，录第二次 | 409（防误操作） |
| 同公司同岗位 + 不同渠道 | 允许，两条记录 |
| 同公司同岗位 + 第 4 个渠道 | **允许**（不限制次数） |

**为什么不限制次数**：
- 唯一约束的语义是"禁止重复"，不是"允许几次"；要限 3 次只能应用层 count，且存在并发竞态
- 投第 4 次同一岗位几乎不会发生；真发生了说明是真实数据，拦住反而错
- **约束用来防误操作，不用来限制业务行为**

**成本**：`migrations/006`（改约束 + 加 `idx_user_source` 索引；005 已被"AI 分析字段"占用）+ `models/job.py` 的 `__table_args__` + `docs/API.md` 附录 A。约 15 分钟。

**已实现**（2026-11-26，迁移 011）：`uk_user_company_position_source` + `idx_user_source`；前后端均支持按渠道分组/筛选。

### 2. 筛选靠 query 参数，不新增接口

`status` / `source` / `q` 三个参数互相独立、可任意组合：

```
GET /api/v1/jobs?source=Boss直聘
GET /api/v1/jobs?q=极光&source=本校
GET /api/v1/jobs?q=Python&status=预约面试&source=Boss直聘
```

"选择搜索范围" = 加一个 `source` 参数，不需要 `/jobs/search` 这类新路由。

**成本**：`crud/job.py` 的 `list_jobs` 加三个可选条件 + `routers/job.py` 加三个 `Query`。约 30 分钟。

### 3. "看起来乱"在展示层解决

放开约束后"全部"列表会出现同公司多行。解法是**前端按 `company` 分组折叠**，不是限制数据。

### 4. 注册：受限开放（已实现）

`REGISTER_OPEN` 开关（默认 false）+ `REGISTER_CODE` 邀请码。开关关闭时连邀请码都不校验。

## 四、延后决策（有明确触发条件）

### 1. 忘记密码 / 邮箱找回（已定方案，等"能被使用"之后再做）

**已定方案（2026-11-24）**：走**完整邮箱找回**，不是"输用户名就能改"。

**为什么明确排除危险做法**：`输入用户名 → 直接改密码` 等于没有密码保护，任何人知道你用户名就能接管账号。这是很多小项目的真实事故。

**方案内容**：
- `users` 加 `email`（唯一，可空）——DDL 见下文「4. 邮箱注册迁移预留」，两件事应合并成一次迁移
- 新表 `password_reset_tokens`：`token_hash`（存 sha256，不存明文）、`user_id`、`expires_at`（15–30 分钟）、`used_at`（一次性）
- `POST /auth/forgot-password`：接收邮箱 → **无论邮箱是否存在都返回同样的 200**（防用户枚举），存在则发重置链接
- `POST /auth/reset-password`：接收 token + 新密码 → 校验未过期未使用 → 改密码 → 标记已用 → **使该用户现有 token 失效**（强制所有设备重新登录）
- 配 SMTP（QQ/163 邮箱授权码，或服务商 API）

**为什么现在不做**：项目当前的真实缺口不是"缺一个功能"，而是**"还不能被真正使用"**——手机和朋友的电脑都访问不到（只有 `127.0.0.1`）。**先让它可用，再加找回密码。**

**该做的信号**：项目已经部署到公网、有 ≥2 个真实用户（包括你自己）在用。

**成本**：1–1.5 天（含迁移、两个接口、邮件模板、前端两个页面、SMTP 调试）。

### 2. 「待定」聚合机制（多次采样）

**设计**：同一 JD 调 1 次拿到档位；若落在临界带则再采 2 次，三次不一致 → 判「待定」，交人工。

**为什么现在不做**（注意：理由不是"省 token"——按"临界带才重采"的设计，稳定岗位只调 1 次，机制在稳定场景下成本为零）：

1. **无法测试**：没有任何输入能触发"不一致"，写出来也是未验证的代码。**未验证的代码比没有代码更危险**——你会盲信一个可能算错的保护。
2. **临界带阈值缺数据**：要定义"多少分算临界"，需要 20+ 个真实分析样本。现在拍一个 `70–80`，太宽则每次都重采，太窄则形同虚设。
3. **最危险的类别已被覆盖**：缺核心能力的岗位由 `blocking_gaps` 规则强制"不建议投递"，100% 稳定，不需要采样。剩下可能飘的只有"无 blocking 且分数临界"的岗位，其占比未知。

**该做的信号**：
- 观察到 **≥3 次**「同一 JD 两次结论不同」，且这些岗位属于「无 blocking、分数 60–80」
- 或者：人工复核时频繁觉得"模型判错了"

**⚠️ 前置动作（现在就做，零成本）**：在分析接口里加一行日志，保留每次的原始分数与档位：

```python
logger.info("AI 分析 job_id=%s score=%s verdict=%s", job.id, result.match_score, result.verdict)
```

现在 `analysis` 字段每次被覆盖，飘没飘看不出来。**有日志才可能用数据回答"要不要做"。**

**成本**：聚合函数约 20 行 + `verdict` 允许"待定"（`VARCHAR(20)`，无需迁移）。现在做和以后做成本几乎相同——所以推迟的依据是 YAGNI，不是成本。

### 3. 状态历史（`status_log` 表）

**为什么有价值**：`jobs.status` 只存当前状态，改了就没了。历史能回答"投了 20 家几家有回应""从已投到预约面试平均几天""我在哪一步卡住最多"——这是策略复盘数据。

**为什么现在不做**：字段缺失不可逆，历史可以后补（建表后 `INSERT ... SELECT` 补初始状态）。

**该做的信号**：
- 记录数超过 30 条，开始想复盘
- 或 `status` 枚举和联动规则稳定了（现在还在改）

**成本**：新表 + `PATCH` 里写日志 + `DELETE` 时先删子表 + `GET /jobs/{id}/logs` 接口。半天。

### 4. 邮箱注册迁移预留

将来从"邀请码注册"升级到"邮箱验证注册"时，需要这三样（现在加成本最低，因为只有 1 个用户）：

```sql
ALTER TABLE users
    ADD COLUMN email VARCHAR(255) NULL,          -- 可空 + UNIQUE（MySQL 允许多个 NULL）
    ADD COLUMN email_verified_at DATETIME NULL,  -- 用时间戳而非 bool，兼答"激活了没"和"什么时候激活"
    ADD COLUMN is_active TINYINT(1) NOT NULL DEFAULT 1,
    ADD UNIQUE KEY `email` (`email`);
```

**同时要做的契约预留**：`LoginIn.name` → `account`（既可以是用户名也可以是邮箱），并禁止用户名含 `@`（否则和邮箱撞名）。

**触发条件**：决定对外开放注册（面向陌生人）时；**或做「忘记密码 / 邮箱找回」时**（两者都要这一列，应合并成一次迁移）。

**为什么现在不做**：功能可后加，且"验证码是 6 位还是链接"这类形状还没定，现在建表八成要迁移两次。

### 5. 多端同时登录

`users.token` 是单列，**同一账号只能一处登录**——手机登录会把 PC 顶下线。

产品形态是"手机 + PC 浏览器插件"，将来必然要同时登录 → 需拆成 `tokens` 表（多行）。

**现在要做什么**：不用做什么，但要**知道这是已知限制**，不要误以为是 bug。
